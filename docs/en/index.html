    Introduction

    The five layers at a glance

    No layer replaces the one below it. It simply manages something bigger.

    Over the last two years, terms ending in "engineering" have multiplied at roughly the rate of model releases. Rolling your eyes is a reasonable response. But these five are not five buzzwords — they are one ladder. Every rung up enlarges the unit you are responsible for, and at the same time moves you further from the work itself.

    The shortest possible summary:

    Prompt engineering manages a sentence. Context engineering manages a window. Harness engineering manages a run. Loop engineering manages the repetition itself. Graph engineering manages how several agents are arranged and connected.

    The layer explorer — click to expand

    Read the stack below from the bottom up. Open each layer to see what it manages, how it fails, and which tools attach to it.

    Unit of concern: the arrangement of several agents and stages. Nodes do work, edges decide the route, state flows over the top.

    Two meanings are tangled together here. ① The execution graph — agents wired as a DAG or state machine. ② The knowledge graph — entities and relations as shared memory. This guide covers both, and keeps them clearly apart.

    Failure mode: no individual node is wrong, and the overall conclusion is. Tracing the cause requires that the graph itself be readable.

    Unit of concern: a repetition that drives itself. It wakes on a timer, spawns helpers, and eats its own output as the next input.

    A change of identity: all three layers below assume a human is at the keyboard. The loop deletes that assumption. You build the loop from outside it, not inside.

    Failure mode: a wrong understanding gets written to a state file, is read the next morning as settled fact, and many turns pile on top of it. By the time anyone notices, that assumption is load-bearing.

    Unit of concern: one entire run of an agent. Which tools, which permissions, which verification, and what counts as "done".

    Definition: the harness = everything except the model. System prompt, tools, sandbox, hooks, permissions, observability.

    Failure mode: the agent acts on a wrong understanding — it edits files. But the run ends and the diff is visible, so a human reviews it before it ships.

    Unit of concern: the whole context window — system prompt, tool definitions, file contents, conversation history, memory.

    The key reframe: context is not infinite storage; it is a finite budget. Every extra token you put in draws down the "attention budget".

    Failure mode: a confidently wrong answer. A human senses something is off and clears the context. It ends within a single reply.

    Unit of concern: one exchange. Assumption: a human is sitting at the keyboard.

    What it covers: phrasing, examples, roles, output format, eliciting reasoning. Failure mode: visible on the spot and fixed on the spot. The smallest blast radius there is.

    The 2026 twist: the list of techniques itself has changed. Prefill is no longer supported on Claude 4.6+, and on reasoning models hand-written step-by-step CoT actively hurts. What died is not "prompt engineering" but 2024-vintage prompt engineering.

    Three core intuitions

    Intuition 1 — each rung up enlarges the "unit of concern"

    This ladder has one rule. Each layer automates the human work left over by the layer below. The prompt layer leaves you "what should I say?" → the context layer automates that. The context layer leaves you "which tools should I hand over?" → the harness layer automates that. The harness layer leaves you waiting for it to finish → the loop layer automates that. The loop layer leaves you "who takes which part?" → the graph layer automates that.

    Intuition 2 — the same bug has a different blast radius at every layer

    This may be the single most important sentence in the guide. The cost of a mistake is proportional to the number of turns it survives before someone notices. And a loop is, structurally, a machine for maximising the number of turns.

    LayerHow the same bug (a misread return value) shows upTime to discovery
    PromptOne answer is wrong. The human sees it immediately and rewrites.Seconds
    ContextA stale doc gets loaded and the model is confidently wrong. The human clears context.Minutes
    HarnessThe agent edits files according to the misreading. The diff is visible, so review catches it.One run
    LoopWritten to a state file → read the next day as settled fact → built upon indefinitely.Days to weeks
    GraphWorker A's misreading enters shared state and contaminates B's and C's conclusions. Every node looks fine.Hard to trace at all
    This is why half of this guide is about verification Evaluators, human checkpoints, budget ceilings, provenance — every safety device that follows is ultimately a device for shortening the distance between a mistake and its discovery. Because the higher you climb, the wider that distance opens on its own.

    Intuition 3 — generation becomes free, judgment becomes scarce

    Loops make code, plans, fixes and PRs nearly free. What becomes scarce is judgment: knowing which plan is right, and knowing whether an output is actually correct rather than merely plausible. A loop can produce a hundred candidates but cannot pick the correct one — it can only pick the plausible one.

    This is the theme that keeps returning: a loop is an amplifier for judgment. Two people can build the same loop and get opposite results. Go in with understanding and it amplifies understanding; go in with laziness and it amplifies laziness.

    Before you read — a freshness warning about the vocabulary

    Let me be straight with you: these five terms are not a standard set by academia or by an AI lab. They were coined by the practitioner community over a handful of months, and their freshness varies wildly.

    Layer 1 · the ground floor

    Prompt Engineering

    Designing what you say to the model

    Anthropic's definition is short: "the practice of writing and organizing LLM instructions to get optimal results." The unit of concern is a single exchange, and the assumption is that a human hands over a prompt every time. That assumption is exactly what the layers above erase, one at a time.

    On the claim that "prompt engineering is dead"

    The argument is still running in 2026. Put precisely: what died is the list of techniques, not the discipline. The evidence is not speculation — it is in the current official documentation of two labs.

    ✕ Dead or counterproductive in 2026
    • Prefill (pre-filling the response) — no longer supported on Claude 4.6+.
    • Hand-written step-by-step CoT — on reasoning models, the model's own reasoning routinely beats the procedure a human specifies.
    • Explicit self-verification instructions — Opus 5 self-verifies without being told, and verification instructions carried over from older prompts cause over-verification, adding tokens and latency for nothing.
    • "You are the world's best …" flattery — no measurable gain has been demonstrated.
    ✓ Still important, or more so
    • Precise scope, constraints and output format — OpenAI's GPT-5.2 guide states outright that "small changes in prompt structure make large differences in accuracy, latency and trust."
    • Examples (multishot) — three to five, structured with <example> tags.
    • XML tag structure — it draws boundaries between instruction, context and input.
    • Long-context ordering — put the question after the documents.
    • General instructions > prescriptive procedure — "think thoroughly" often beats a hand-written list of steps.

    "Prefer general instructions over prescriptive steps. A prompt like 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan. Claude's reasoning frequently exceeds what a human would prescribe."

    Anthropic prompting best-practices documentation · Chain of Thought section (checked July 2026)

    The anatomy of a good prompt

    The order is not arbitrary. Models respond more strongly to later tokens (see the U-curve in chapter 2), and Anthropic's own testing found that putting long material first and the question last improves response quality on complex multi-document inputs by up to 30%.

    Prompt caching — the biggest practical win available at layer 1

    For workloads that resend the same prefix over and over — which is precisely what an agent loop does — caching should be the default, not an option. The numbers are simple.

    0.1×Cache read
    90% off the base input price
    1.25×Cache write (5 min)
    Pays for itself from the second call
    2.0×Cache write (1 hour)
    For long agent loops

    Only three things about the mechanics are worth memorising.

    • There is a hierarchy: Tools → System → Messages. Change an earlier layer and everything after it is invalidated. Which is why putting the unchanging things first lines up exactly with the ordering in Figure 1-1.
    • At most four breakpoints per request, and the next request looks back up to 20 positions to find a previous entry.
    • Below the minimum token count it is silently ignored — not an error. The threshold varies by model: 512 / 1,024 / 2,048 / 4,096 tokens. Check the official docs for current values.
    The practical rule Design every prompt as "an immutable prefix plus a variable suffix." System prompt, tool definitions, bulk reference documents and examples go in the prefix. Only this turn's question goes in the suffix. That single arrangement determines most of the cost of a repeated call.

    Layer 2

    Context Engineering

    What has to be inside the window

    If prompt engineering is "what do I say?", context engineering is "what is in the model's entire field of view?" — system prompt, tool definitions, retrieved documents, conversation history, memory. Everything that flows into the window from outside the prompt.

    "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference, including all the other information that may end up there outside of the prompts themselves."

    "Unlike writing a prompt, which is a discrete task, context engineering is iterative, and the curation phase happens each time we decide what to pass to the model."

    Anthropic, "Effective context engineering for AI agents" (September 2025)

    The attention budget — why "just put it all in" fails

    The window went from 200K to 1M, so why not just put everything in? The answer is no, and the reason is architectural rather than a matter of taste.

    The mechanical reason: a transformer lets every token attend to every other token. With n tokens there are n² pairwise relationships. The longer the context, the more thinly stretched the model's capacity to capture those relationships becomes.

    Which is why Anthropic calls it an attention budget. Every token you add draws it down a little. Context is not storage; it is a finite resource with diminishing marginal returns.

    "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome."

    Anthropic (a sentence repeated twice in the same post)

    Evidence ① — Context Rot

    In July 2025, Chroma Research measured 18 models (Claude, GPT, Gemini and Qwen families), varying nothing but input length. The conclusion:

    "Models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows."

    And again, elsewhere in the report — performance "can vary significantly as input length changes, even on simple tasks."

    Chroma Research, "Context Rot" (2025-07-14) · two separate sentences from the report

    The two most counterintuitive findings:

    • On LongMemEval, the identical question scored far higher with a ~300-token compressed prompt than with the full ~113K-token prompt. This held across every model family, and the gap was widest on the Claude family.
    • Performance was worse when the haystack preserved its logical flow. Shuffling it to destroy local coherence consistently improved results. In other words, the problem is not the quantity but the way it is presented.

    Evidence ② — Lost in the Middle

    The classic experiment by Liu et al. (Stanford / Berkeley, TACL 2024). Move the document containing the answer to the front, the middle and the back of the context, measure accuracy, and you get a U-curve.

    Four ways long context fails

    Drew Breunig's taxonomy is the one most widely used. Its value is that each mode needs a different remedy.

    ① Context Poisoning

    A hallucination or error enters the context and is then referenced repeatedly.

    Case: a Gemini agent playing Pokémon hallucinated the game state, contaminated its own "goals" section, and then pursued impossible objectives from there on.
    Remedy: provenance (tagging each piece of information with the document or tool it came from), state validation, periodic resets.

    ② Context Distraction

    The context grows so long that the model over-focuses on it at the expense of its trained knowledge.

    Case: past roughly 100K tokens, Gemini 2.5 Pro tended to repeat actions from its vast history rather than form new plans.
    Remedy: summarisation and compaction.

    ③ Context Confusion

    Superfluous material is actually used, producing a low-quality response.

    Case: every model got worse as the number of tools grew. A quantised Llama 3.1 8B failed with 46 tools and succeeded once the set was cut to 19.
    Remedy: tool loadout and pruning.

    ④ Context Clash

    New information or tools contradict what is already there.

    Case: in research from Microsoft and Salesforce, splitting requirements across several turns cost an average 39% drop in performance. The paper reports this is not specific to one model — it was observed across all of them.
    Remedy: context quarantine; restate the requirements and restart.

    Number ④ is the one that happens most often, and most quietly, in real work A chat window where you have said "no, not that — do it this way" ten times is a context holding ten contradictory sets of requirements. The model has no idea which is current. Once the requirements have settled, /clear and start again with one clean prompt — that almost always wins.

    ③ /compact and automatic compaction

    As the window approaches its limit, Claude Code compacts automatically. The mechanism: analyse the conversation → produce a summary that "preserves architectural decisions, unresolved bugs and implementation details while discarding redundant tool output and messages" → replace the old messages with that summary.

    What matters is what survives compaction.

    ItemAfter compaction
    System prompt / output styleunchanged (it is not message history)
    Project-root CLAUDE.mdre-injected from disk
    Auto memoryre-injected from disk
    Nested CLAUDE.md in subdirectorieslost — until you read a file in that directory again
    Rules carrying paths: frontmatterlost — until you read a matching file again
    The body of an invoked skillre-injected, capped at 5,000 tokens per skill / 25,000 total

    You can also steer it by hand: /compact keep only what relates to the payment retry logic. And between unrelated tasks the right command is /clear, not /compact — compaction does leave a summary behind, but a summary of a different task is just noise in the next one.

    What a harness is made of

    The agentic loop — what the harness turns

    This is the shape Anthropic defines explicitly in the Claude Agent SDK documentation. These four steps are the skeleton of chapter 3, and the inner rotation of the "loop" in chapter 4.

    "In Claude Code, Claude operates in a specific feedback loop: gather context → take action → verify work → repeat."

    Anthropic, "Building agents with the Claude Agent SDK"

    Tool design — the most visible part of a harness

    Anthropic's "Writing effective tools for agents" is the densest primary source available. Six principles:

    1. Choosing the tools is already design

    "More tools do not always produce better outcomes. A common failure mode is tools that simply wrap existing software functionality." Consolidate five API calls into one high-value tool. A 1:1 wrapper only eats context.

    2. Namespacing

    With many tools, group them behind a shared prefix (jira_*, db_*). It helps the model perceive the boundaries.

    3. Return meaningful context

    "Prioritise contextual relevance over flexibility." Do not emit raw UUIDs; resolve them to human-readable names. If the model has to re-resolve that UUID next turn, you paid for the tokens twice.

    4. Token efficiency

    Implement pagination, range selection, filtering and truncation — with sensible defaults. A single tool that emits 30,000 tokens has effectively ended that run.

    5. A tool description is a prompt

    "Small refinements to tool descriptions can yield dramatic improvements." Write it the way you would onboard a new colleague — what it does, when to use it, and when not to.

    6. Evaluation-driven development

    This is the heart of the methodology. Build a realistic multi-step evaluation, then have the agent analyse its own transcripts and fix the tools. "Use agents to build tools for agents."

    MCP in one line The Model Context Protocol is "a USB-C port for AI applications" — the standard by which a harness touches the outside world. Adoption is broad, but security is immature — vulnerabilities keep being reported in public servers, so put a trust boundary around them.

    Verification — the real product of a harness

    "Give the agent a way to check its own work" sounds abstract. Anthropic breaks it into three concrete channels.

    Guides vs sensors

    Thoughtworks' Böckeler splits harness controls into two kinds. The distinction is genuinely useful in practice.

    Guides — feed-forward

    Point the agent in a direction before it acts. CLAUDE.md, skills, tool selection, permission rules, plan mode.

    Sensors — feedback

    Observe after it acts and let it correct itself. Tests, lint, LSP diagnostics, screenshots, evaluator agents.

    "A good harness doesn't have to aim at removing human input entirely. The goal is to direct our input to where it matters most."

    The field that matters most — how to write a description

    When a skill never fires, the cause is almost always the description. You have to say what it does and when to use it.

    ✕ Descriptions that never fire
    • description: Code review
      — no indication of when to use it
    • description: A skill containing our team's excellent review process
      — that is self-promotion, not a trigger condition
    • description: Useful in a wide variety of situations
      — matches every request a little, so it fires everywhere
    ✓ A description that fires correctly

    description: Find await calls in src/ with no error handling and classify them by risk. Use when the user asks to "check error handling", mentions "unhandled promise" or "missing exception handling", or asks for a pre-deploy check. Does not modify code.

    The structure: ① one sentence on what it does → ② "use when …" plus three phrasings a real user would type → ③ one line on what it does not do. That last item is what prevents misfires.

Include a finding only if one of the three below applies.

1. **External I/O** — network, DB, filesystem (failure is a normal occurrence)
2. **Parsing external input** — `JSON.parse`, zod `parse`, form decoding
3. **Money or data at risk** — payments, orders, inventory

    # Rules for judging borderline cases

## Counts as category 1
- all of `prisma.*` (connection pool exhaustion, deadlocks)
- `fetch`, `axios`, `stripe.*`
- every function in `fs/promises`
- `redis.*` — a cache miss is fine, a connection failure is not

## Does not count as category 1
- `await Promise.all([...])` itself — judge each inner call separately
- `await sleep(ms)`, `await nextTick()` — no failure path
- calls that pass through a wrapper which already wraps in `AppError`

## When a caller counts as wrapping it
Only when the direct caller has a `try/catch` and that catch either does not
rethrow or rethrows wrapped in `AppError`.
`catch (e) { throw e }` is not wrapping.

## Special rule for Fastify routes
Fastify catches rejections in route handlers automatically and returns a 500.
So report a top-level await in a route handler only for category 3
— the 500 going out is not the problem; the partially committed state is.

  rm -f "$GUARD"; exit 0

#   Without this you have an infinite loop.

  rm -f "$GUARD"
  jq -n '{ systemMessage: "The gate has failed 3 times. A human should take a look." }'
  exit 0
fi

fail() {
  echo $((n + 1)) > "$GUARD"
  jq -n --arg o "$1" '{ decision: "block", reason: $o }'
  exit 0
}

tc=$(pnpm typecheck 2>&1) || fail "Typecheck failed. Fix it and continue:"$'\n'"$tc"
ut=$(pnpm test:unit 2>&1) || fail "Unit tests failed:"$'\n'"$ut"

rm -f "$GUARD"
exit 0

## Check in this order

1. **Does it run** — do not read it, run it.
   Execute `pnpm typecheck` and `pnpm test:unit` yourself and paste the output.
2. **Do the tests actually verify anything** — check whether a passing test

4. **Does the behaviour match the requirement** — compare against the

- Otherwise `REJECT`, listing the failed items by number, each with

- "Looks fine" is not a verdict. Give evidence.

- Do not modify code. (You have no tools for it, so this is impossible anyway.)
- Do not manufacture findings. If there are none, say `PASS`.

    Building a system that runs itself

    The three verbs one floor up actually adds

    ⏰ It turns on a timer

    It wakes on a schedule, not on a human's click. The first condition of a loop.

    👥 It spawns helpers

    One agent drafts; a different agent takes it apart.

    ♻️ It eats itself

    Yesterday's findings are written to a file, and this morning it reads them and continues. Memory that outlives the conversation is what makes a loop a loop.

    Without all three, it is not a loop. Running the same task several times is not a loop — it is several runs.

    The hardest part — generator and evaluator

    The hard thing about a loop is not making the agent turn. It is putting something inside it that can say "no". And the agent that wrote the code is the agent least likely to say it.

    Agents always praise themselves

    "When asked to evaluate work it produced itself, an agent tends to praise it confidently — even when the quality is plainly mediocre to a human observer."

    Prithvi Rajasekaran, Anthropic — on harness design for long-running agent applications

    This is not a problem of intelligence but a problem of grading your own homework. The context in which the code was written is already full of the reasons it was written that way. So when the agent looks at its own output it does not see a result — it sees the chain of self-persuasion that led there.

    The fix is structural, not a matter of prompting

    "Tuning a standalone evaluator to be sceptical turns out to be far more tractable than making a generator critical of its own work. And the moment that external feedback exists, the generator has something concrete to aim at, repeatedly."

    Prithvi Rajasekaran, Anthropic

    The difference is not phrasing but structure. You cannot ask an author to step outside their own perspective, but you can swap in a different agent with entirely different instructions — one that reads the code from scratch and carries none of the self-persuasion with it.

    The evaluator has to act, not read

    Swapping in a different agent is not enough on its own. For front-end work, Anthropic's Rajasekaran wired the evaluator to Playwright MCP so it would open the page, click buttons, take screenshots, and inspect the DOM the way a QA engineer does. The basis for the judgment shifts from "this JSX looks fine" to "I clicked the button, the page navigated, and here is the screenshot."

    Four quiet costs — nothing raises an alarm

    A loop that runs itself is simultaneously a loop that makes mistakes by itself. The more happily it turns, the more happily it is wrong. Four costs accumulate, and none of them sets off an alarm while the loop is running.

    What it actually looks like — one night

    The loop opened 20 PRs overnight and every one is green. On the surface, a success. Except:

    • Three contain subtle errors the tests do not cover. With no independent evaluator they merge as they are → verification debt
    • Nobody read all twenty before merging, so your mental map of the codebase is twenty changes out of date → comprehension rot
    • The loop went so smoothly that tomorrow morning's batch does not get read at all → cognitive surrender
    • The loop spawned helpers and retried all night, so the bill is 3× the estimate → token blowout

    Those three buried errors now sit inside a codebase nobody fully understands any more, watched over by someone who has stopped looking. Eventually one of them is discovered by going off in production.

    Defences against each cost

    CostDefenceWhy that one
    Verification debtAn independent evaluator — a different agent from the one that did the workSelf-grading fails structurally (see above)
    Comprehension rotRead a sample every day, and force yourself to explain the changes you sampledReading everything defeats the purpose. Being unable to explain something is the precise signal that your map needs updating. Finding that out in a PR on a quiet morning is far cheaper than finding it out in a production incident on a bad day.
    Cognitive surrenderLeave one door open — keep a checkpoint that stops for a human, structurallyNot because a human always intervenes, but because the existence of the stop keeps the human in a position where they could. The engineer who welds every door shut discovers, on the day they need to get in, that they no longer hold a key.
    Token blowoutHard ceilings before you deploy — a per-run budget, a daily budget, a maximum retry countThese numbers are not a cost-saving device; they are circuit breakers. They convert open-ended risk into bounded risk. A loop with no ceiling is a loop that has delegated spending authority to its own bugs.
    One real incident — gaps in the harness become attack surface A vulnerability disclosed in June 2026 in the claude-code-action GitHub Action: the trigger check allowed through any actor whose name ended in [bot]. Reported January 2026 → patched in four days (v1.0.94) → CVSS 7.8.

    The lesson: an unattended loop is unattended attack surface. Draw the trust boundary in code.

    Two loops actually running

    ① One person's morning — Osmani's triage loop

    In the morning the automation starts by itself. A triage skill reads yesterday's failed CI runs, the still-open issues and the recent commits, and writes the result to a markdown file (or a Linear board). Anything it cannot handle goes to an inbox that waits for a human. A state file persists, so the next day picks up where it stopped.

    No step needs a hand, and it stops in exactly the places where one is needed. This is a one-person-scale loop — one person, one machine, the chores of every morning.

    The economics of judgment

    This is not a slogan but an economic observation. When a resource becomes abundant its price falls, and the activity organised around it is reorganised.

    What becomes abundant

    Code, plans, fixes, PRs. One engineer with a good loop can produce the output of a small team. The typing, boilerplate and mechanical refactoring that used to consume an engineer's day collapse to near-zero cost.

    What becomes scarce

    The judgment that decides which output to keep. A loop can produce hundreds of plausible implementations but cannot tell you which is correct — only which looks plausible. The gap between "looks plausible" and "is actually right" is precisely where engineering lives.

    There is an uncomfortable implication here. The engineer whose value lay mostly in mechanical labour — fast typing, broad API recall, the willingness to grind out boilerplate — watches that value evaporate, because the loop does all of it for free. The engineer whose value lay in judgment watches it get amplified, because the loop executes their good decisions a hundredfold.

    "Because a loop amplifies judgment, it amplifies errors of judgment too. In the old world one bad decision was one lump of wrongly hand-written code — limited blast radius, slow enough to catch. In the new world one bad decision is executed faithfully, at volume, a hundred times over by a machine — a machine that never stops to ask whether it was right."

    "Build the loop. But build it like someone who intends to stay the engineer, not just the person who presses go."

    Addy Osmani, "Loop Engineering", closing line

Rule on every candidate:

- **Is it actionable now?** No way to reproduce it means it is noise → drop it

- **Is it already in `state/triage.md`?** → skip it (no duplicates)
- **Does it touch `src/payments/`?** → priority=P1 and human review is mandatory

Keep only what is genuinely worth touching today. At most five.
Above five, cut from P1 downwards — never hand the loop more than it can carry.

    Who does what, in what order, sharing what

    The 30-second version — a graph is an org chart

    Before any of the hard vocabulary, look at a picture. What we built through chapter 4 was one generalist employee. They come in every morning, find the work, fix it, check it, write it down, and schedule tomorrow. Alone, in order.

    A graph splits that one person into several and wires up who does what, when. That is all it is.

    5A. Execution graphs

    A loop is a line; a graph is an arrangement

    From loop to graph — four stages

    A loop is already a special case of a graph: one node with a single arrow returning to itself. Let us see how it grows from there.

    There are exactly three reasons to widen

    ① The context does not fit

    One agent has to read material from five domains and the window is not big enough.
    shopmate example: a migration that requires seeing frontend, backend, infra and the DB schema at once

    ② You need viewpoints

    One pass misses things. You need independent looks through different lenses, then a comparison.
    shopmate example: security eyes and performance eyes catch different things

    ③ Scale

    The same transformation has to be applied to 500 files. That exceeds what one conversation can coordinate.
    shopmate example: adding zod schemas to every route

    If none of the three applies, do not build a graph "It looks impressive" and "everyone's doing it" are not reasons. A graph is a structure whose failure surface grows multiplicatively. In a five-node graph, the number of combinations you have to debug is not five.

    The basic grammar — five patterns, one at a time

    The taxonomy Anthropic published in December 2024 (Schluntz & Zhang) is still the vocabulary of this field. Before it, one decisive distinction:

    "Workflows are systems where LLMs and tools are orchestrated through predefined code paths.
    Agents … are systems where LLMs dynamically direct their own processes and tool usage."

    Anthropic, "Building Effective AI Agents" (2024-12-19)

    Graph engineering sits mostly on the workflow side — taking control back from the model and into code. The five patterns below are five ways to wire those code paths.

    The basic block — the augmented LLM

    ① Prompt chaining — fixed stages plus code gates

    ② Routing — classify, then send to a specialist

    ③ Parallelisation — divide it up (sectioning), or do it repeatedly (voting)

    Let us head off one misreading first — a "lens" is not a perspective, it is a unit of execution The phrase "correctness · security · performance lenses" recurs from here on. It does not mean one agent looking at three things in sequence. One lens = one agent = one process = one context. All three start at the same time, each with its own context window, and each finishes without ever seeing what the others found.

    Which is why it costs three times as much. You did not split a prompt into three paragraphs; you made three model calls. And that is also why it pays — precisely because they cannot see each other, one catches what another missed. It is a different thing from following up inside the same context with "now look at it from a security angle." That follow-up is already coloured by everything it just said.
    So how many do you split into? N is free — but you decide it differently in each case

    This guide keeps saying "three lenses". Three is not a rule; it is this example's (shopmate's) choice. Add one line to the LENSES array and you have four. But the basis for choosing N is completely different for sectioning than for voting.

    N in sectioning — you are not counting, you are naming

    N = the number of failure types you can name without overlap. "Correctness, security, performance" is three not because three is a nice number, but because in this codebase those are exactly the viewpoints that catch different things.

    When to add one: when there is another type you can name. Accessibility, i18n, migration safety, API compatibility — any axis on which your team has actually had an incident qualifies as a lens.

    When not to: when the new lens catches the same things as an existing one. Add a "code quality" lens and half of it overlaps correctness. Then you pay tokens for duplicate findings and add work to the merge stage to strip those duplicates back out.

    N in voting — here it is odd, and it stops early

    Asking the same question repeatedly is a statistics problem. Odd numbers (3, 5) to avoid ties is the baseline, and the value falls off sharply above that.

    The October 2025 paper Self-Consistency Is Losing Its Edge reports that on current models, accuracy flattens early as you add samples and in some settings actually declines — on MATH-500 it peaks around 10 and falls past 15. On Gemini-2.5-Pro, "15 paths spent 15× the compute to recover 1.6%"; on HotpotQA, 20 samples bought 0.4%.

    Which is why exercise 5-A puts three verifiers on each finding. You can raise it to five, but before you do, making the verifiers' prompts differ from one another almost always pays better.

    The calculation you must do before raising N Anthropic states that multi-agent setups use 3–10× the tokens for the same work, and adds one decisive sentence — "the main gain from parallelisation is thoroughness, not speed." Adding a lens is a cost decision, not a speed decision. So before you add one, you should be able to answer: "have we actually had an incident that only this lens would have caught?" If not, that lens just spends tokens.

    ④ Orchestrator–worker — when you cannot know the subtasks in advance

    In ③ parallelisation, I decided in code that there would be "three lenses". But some work is such that you cannot know in advance how many are needed or what to assign them.

    shopmate example: "Investigate whether this release is safe." — what should you look at? If the changed files only touch payments, one payments investigation is enough; if a schema migration is in there, you need a DB investigation as well; if dependencies were bumped, you need a vulnerability sweep too. You cannot build the list before you see the input. That is when an orchestrator builds the list at runtime and spawns workers.

    The price: the flexibility costs you control. You do not know in advance how many workers will start, so you do not know the cost in advance. In practice, people therefore put ceilings on it — a maximum worker count, a per-run token cap. It is also why exercise 5-A uses ③ parallelisation instead: three lenses are knowable in advance, so there is no reason to give up control.

    ⑤ Evaluator–optimiser — the structure from chapter 4

    The five patterns are not exclusive — composing them is normal Real systems usually layer them like this:
    ② Routing filters out payment changes → ③ parallel sectioning puts three lenses on it → ⑤ an evaluator tries to refute each finding → ① a code gate filters → one result.
    That is the graph you will actually build in exercise 5-A.

    Nodes, edges and state — how a graph actually turns

    LangGraph's one-line summary is the clearest: "nodes do the work, edges tell it what to do next." Of the three, state is the hardest to grasp. Let us look at a picture.

    ElementIn plain termsWhat it means in practice
    StateThe folder the whole graph passes aroundA node returns only a partial update — never a full rewrite. That is what reduces merge conflicts.
    NodeThe person who takes the folder and fills one fieldA node does not have to be an LLM. An ordinary function is fine — the point of the next section.
    EdgeWhere the folder goes nextA static edge always goes to the same place; a conditional edge looks at the state and picks a branch. Conditional edges create both branching and cycles.
    CheckpointA saved copy of the folder at each stepFailure recovery, resumption, rewind. Non-negotiable for long runs.
    InterruptStopping in front of a human, folder in handChapter 4's "leave one door open" becomes a first-class feature in a graph.
    There is exactly one mechanical difference between a chain and a graph A chain cannot contain a cycle; a graph can. Whether you can express "if the result is unsatisfactory, send it back" — that is the whole of it. Chapter 4's loop is, in the end, one conditional edge pointing at itself.

    The most confusing part — do you wait, or do you let it flow?

    This is where people go wrong most often when they actually write a graph. The concept is simple but hard to hold without a picture.

    The barrier style (parallel)

    Stage 2 does not begin until all of stage 1 has finished.
    "Verification starts once all three reviews are done."

    The pipeline style

    Each item passes through every stage independently.
    "The correctness review is done, so put that one into verification now."

    Which is why the default is a pipeline A barrier is justified only when the next stage needs the results of the entire previous stage.
    ✓ When a barrier is justified
    • You need to deduplicate across everything first
    • Early exit: "if there are zero findings, skip verification entirely"
    • The verifier prompt refers to "compared with the other findings"
    ✕ What does not justify a barrier
    • "I need to flatten/map/filter first" → do that inside a pipeline stage
    • "The stages are conceptually separate" → separate ≠ synchronised
    • "The code is cleaner" → wait time is a real cost

    The most important design principle — what goes in code, what goes to the model

    "Deterministic facts must be guaranteed by software. Probabilistic judgment must be delegated to the model explicitly, and narrowly."

    Microsoft ISE engineering blog (2026-06)

    In the case described in that post, schema compliance moved from 0% to 100%. Not by fixing the prompt but by moving the work. The author's sentence goes straight to the point — "There was nothing wrong with the prompt. The problem was asking the LLM to do a job software should have owned."

    The lesson of 2026 — parallel reads work, parallel writes do not

    The most instructive argument in this field. Read two posts by the same author a year apart and you can watch the industry's understanding mature.

    June 2025 — "Don't build multi-agents"

    Walden Yan of Cognition. The core argument: context sharing between parallel agents breaks down.

    "Actions carry implicit decisions, and conflicting decisions produce bad results." Recommendation: a single-threaded linear agent, with a dedicated LLM compressing the history.

    April 2026 — "Multi-agent, what actually works"

    The same author, a year later. The position did not reverse — it got precise.

    "Multi-agent systems work best when writes stay single-threaded and the additional agents contribute intelligence rather than actions."

    The rule to memorise, in one line Parallelise reading, proposing and voting freely. Exactly one node ever holds write permission.

    And if you genuinely must edit files in parallel, use worktrees to give each one its own copy — the point is not to write to the same file simultaneously but to arrange that they write to different files in the first place.

    Three patterns reported to actually work in 2026 (Cognition)

    • The code-review loop — a reviewer agent working from clean context (it never sees the coder's full history). Reported: an average of 2 bugs found per PR, of which roughly 58% were serious.
    • The "smart friend" — the main model consults a stronger one. Deployed when both are strong, and across frontiers (Claude + GPT).
    • Manager/child delegation — still requires substantial context-engineering work.

    What does not work: parallel writer swarms, unstructured agent networks. "Most of the sexy ideas in that space still haven't seen meaningful adoption"; "mostly a distraction."

    5B. Knowledge graphs

    What the agents share

    The problem — five people working in five separate rooms

    In 5A we split the work across several agents. The moment you split it, a new problem appears. None of them knows what the others saw. And when the conversation ends, what they saw disappears with it.

    One sentence A knowledge graph is the structured version of "agents forget; repositories do not" (chapter 4's state file). It uses nodes and edges instead of a markdown table, which means you can walk across it.

    Why RAG cannot do this — one picture

    "Couldn't you just do this with retrieval?" is the natural question. Here is why not, in a picture.

    The four-stage pipeline — all of it in prompts

    The classical approach needed a trained model at every stage: an NER model, a relation classifier, hand-built resolution heuristics. Change the domain and you re-label and retrain. An LLM-based pipeline replaces the whole thing with a sequence of prompts. The "training data" is a single Pydantic schema (the Python schema library equivalent to zod in TypeScript).

    What actually happens to the data — in one picture

    Read abstractly, this does not stick. Let us follow what shape the same data takes as it passes through the four stages.

    Stage 1 — extraction: skip structured output here and everything downstream collapses

    python — the schema is the contract
    from pydantic import BaseModel
from typing import Literal

EntityType = Literal["PERSON", "SERVICE", "INCIDENT",
                     "DECISION", "COMPONENT"]

class Entity(BaseModel):
    name: str
    type: EntityType
    description: str      # one line. The only weapon stage 2 will have.

class Relation(BaseModel):
    source: str
    predicate: str        # short verb phrase: "modified", "caused", "owns"
    target: str

class ExtractedGraph(BaseModel):
    entities: list[Entity]
    relations: list[Relation]


def extract(text: str) -> ExtractedGraph:
    # output_format is the entire interface specification.
    # No parsing. No validation. No silent errors.
    response = client.messages.parse(
        model="claude-haiku-4-5",        # high volume · schema-constrained → cheap model
        max_tokens=2048,
        messages=[{"role": "user",
                   "content": EXTRACTION_PROMPT.format(text=text)}],
        output_format=ExtractedGraph,
    )
    return response.parsed_output   # a typed Python object
    Four lines in the extraction prompt prevent four failure modes
    1. "Extract only entities central to what this document is about — skip passing mentions" → deliberately trades recall for precision. At scale one wrong entity spawns several wrong relations, so the trade is correct.
    2. "For each entity, write a one-sentence description grounded in this document" → the decisive signal for stage 2. Without it, resolution guesses from names alone. "exponential backoff → payment retry" in Figure 5-18 is decided right here.
    3. "Predicates must be short verb phrases" → "was related to" is too vague to reason over; "caused" is not. Narrowing the vocabulary is what makes the graph traversable.
    4. "Every relation must connect two entities you extracted" → prevents orphan edges that reference entities which do not exist.

    Stage 2 — resolution: the heart of the pipeline

    Raw extraction produces overlapping mentions. Build the graph from them directly and you get a mess in which the same concept is split across unconnected nodes. A picture makes it obvious.

    The traditional approach is edit distance plus blocking rules. That works for typos and falls apart on "Edwin Aldrin" vs "Buzz Aldrin" — the same person with not one character in common. So you hand the model the one-line descriptions from stage 1 as context and let it do the clustering.

    Failure mode A — silent node loss

    If a raw entity ends up in no cluster, it disappears from the graph, because there is no entry for it in the alias map.

    Defence: fall back to a singleton cluster for any unmatched name. (That is the one setdefault line in the exercise 5-B code.)

    Failure mode B — over-merging

    On the strength of overlapping descriptions, "Gemini 12" gets folded into the broader "Project Gemini". You lose precision.

    Defence: state explicitly in the prompt that "genuinely distinct entities keep their own cluster."

    At scale the answer is a hybrid. Putting ten thousand PERSON entities in one prompt does not work. Use cheap signals first — shared surname, token overlap, embedding similarity — to block them into groups of 50–100, and let the model arbitrate only within a block. Deterministic blocking plus expensive LLM arbitration is exactly the principle of Figure 5-12: spend the model only where judgment is needed and leave the rest to deterministic logic.

    Grounded vs ungrounded — the real difference

    Ungrounded: Claude pulls in pretrained knowledge and gives a comprehensive and probably accurate answer about the Apollo 11 crew and their relationships to various places.

    Grounded: the answer is restricted to the extracted edges — "the only person–place relation the graph supports is Neil Armstrong → walked on → Moon." Less impressive, and incomparably more useful: it is traceable, it is limited to what the corpus actually says, and it makes explicit what the graph does not contain. On a private corpus, only the second kind of answer works at all.

    A. Execution graph — widening triage to three lenses

    Triage so far has been one agent making one pass. Its blind spot becomes the system's blind spot. Split it into three independent lenses, and attach a verifier to each finding whose job is to refute it.

    First — where do agent, pipeline, parallel and log come from in this script? You do not import them. They are functions the workflow runtime injects as globals when it executes the script. That is why there is no require or import anywhere in the file.
    • agent(prompt, opts) — spawns one subagent and returns its result. Pass schema and structured output is enforced.
    • pipeline(items, stage1, stage2, …) — runs each item through all stages independently (Figure 5-11).
    • parallel([thunks]) — a barrier. It waits for all of them.
    • log(string) — shows progress to a human.
    Careful: this is plain JavaScript. Type annotations (: string[]) fail to parse. And Date.now() / Math.random() are unavailable because they would break resume.
    .claude/workflows/triage-graph.js
    // Save at: .claude/workflows/triage-graph.js
// This is plain JS, not TypeScript. Type annotations fail to parse.

export const meta = {
  name: 'triage-graph',
  description: 'Review the diff through three parallel lenses and adversarially verify each finding',
  phases: [
    { title: 'Review', detail: 'correctness / security / performance lenses look at once' },
    { title: 'Verify', detail: 'an independent verifier tries to refute each finding' },
  ],
}

// ── Structured output schemas: these are the "contract" between nodes ──
const FINDINGS = {
  type: 'object',
  properties: {
    findings: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          title:    { type: 'string' },
          file:     { type: 'string' },
          line:     { type: 'integer' },
          severity: { type: 'string', enum: ['blocker', 'major', 'minor'] },
          scenario: { type: 'string', description: 'a concrete failure scenario' },
        },
        required: ['title', 'file', 'line', 'severity', 'scenario'],
      },
    },
  },
  required: ['findings'],
}

const VERDICT = {
  type: 'object',
  properties: {
    refuted: { type: 'boolean', description: 'true if the refutation succeeded' },
    reason:  { type: 'string' },
    evidence:{ type: 'string', description: 'the command run and its output' },
  },
  required: ['refuted', 'reason'],
}

// ── Node definitions: lenses that never see each other ────────────────
// Three is not a rule; it is this repository's choice. Add a line and you have N.
// See "widening the graph" for the criterion — overlapping lenses only cost tokens.
const BASE = `Target: the changes in git diff origin/main...HEAD.
Follow the project rules in CLAUDE.md. Do not modify code.
Do not report anything you are not confident about — noise costs more than a miss.`

const LENSES = [
  { key: 'correctness', prompt: `${BASE}
    Lens: correctness. Look only at logic errors, edge cases (null / empty array /
    concurrent requests) and the state left behind after a partial failure.
    Security and performance are other agents' jobs.` },
  { key: 'security',    prompt: `${BASE}
    Lens: security. Look only at missing authn/authz, input validation,
    secret exposure, and SQL/command injection.` },
  { key: 'perf',        prompt: `${BASE}
    Lens: performance. Look only at N+1 queries, awaits inside loops,
    redundant recomputation, and unindexed lookups.` },
]

// ── Running the graph ─────────────────────────────────────────────────
// pipeline = no barrier. A finding from 'correctness' moves into verification
// while 'security' is still running. This should be your default.
const results = await pipeline(
  LENSES,

  // Stage 1 — find
  lens => agent(lens.prompt, {
    label: `review:${lens.key}`,
    phase: 'Review',
    schema: FINDINGS,
  }),

  // Stage 2 — an independent verifier per finding. The crux is that the
  //           prompt says "refute this", not "confirm this".
  (review, lens) => parallel(
    (review?.findings ?? []).map(f => () =>
      agent(`Refute the following claim.

Claim: ${f.title}
Location: ${f.file}:${f.line}
Scenario: ${f.scenario}

Read the file and its call sites, and where possible actually run the tests
to show that this scenario does not reproduce.
If you are unsure, the default is refuted=true.`, {
        label: `verify:${lens.key}/${f.file}`,
        phase: 'Verify',
        schema: VERDICT,
      }).then(v => ({ ...f, lens: lens.key, verdict: v }))
    )
  ),
)

// ── Deterministic gate: this filtering is done by code, not an LLM. ───
const all = results.flat().filter(Boolean)
const survived = all.filter(f => f.verdict && f.verdict.refuted === false)

// When several lenses land on the same file:line, merge them into one.
const byLoc = new Map()
for (const f of survived) {
  const k = `${f.file}:${f.line}`
  if (!byLoc.has(k)) byLoc.set(k, { ...f, lenses: [f.lens] })
  else byLoc.get(k).lenses.push(f.lens)
}

const RANK = { blocker: 0, major: 1, minor: 2 }
const final = [...byLoc.values()].sort((a, b) => RANK[a.severity] - RANK[b.severity])

// ★ Always log what was cut — a silent truncation reads as "we covered everything".
log(`${all.length} findings → ${survived.length} survived verification → ${final.length} after dedup`)

return { findings: final, dropped: all.length - survived.length }

    """Build a knowledge graph from the markdown in docs/ and answer multi-hop questions.

Dependencies:  pip install anthropic pydantic networkx
Run:           python scripts/kg.py build   →  graph.json
               python scripts/kg.py ask "who touched payment retries?"
"""
import json, sys, pathlib
from typing import Literal
import networkx as nx
from pydantic import BaseModel
from anthropic import Anthropic

client = Anthropic()
EXTRACT_MODEL   = "claude-haiku-4-5"    # high volume · schema-constrained → cheap model
REASONING_MODEL = "claude-sonnet-4-6"   # where judgment is needed → the better model

# ══ The schema is this pipeline's only "training data" ═══════════════
EntityType = Literal["PERSON", "SERVICE", "INCIDENT", "DECISION", "COMPONENT"]

class Entity(BaseModel):
    name: str
    type: EntityType
    description: str          # one line. The only weapon stage 2 has.

class Relation(BaseModel):
    source: str
    predicate: str            # short verb phrase: "owns", "caused", "modified"
    target: str

class ExtractedGraph(BaseModel):
    entities: list[Entity]
    relations: list[Relation]

class Cluster(BaseModel):
    canonical: str            # the most complete form
    aliases: list[str]        # every surface form

class Resolved(BaseModel):
    clusters: list[Cluster]

# ══ Stage 1 · extraction ═════════════════════════════════════════════
EXTRACT_PROMPT = """Extract a knowledge graph from the document below.

<document source="{src}">
{text}
</document>

Instructions:
- Extract only entities central to what this document is about — skip passing mentions.
- For each entity write a one-sentence description grounded in this document.
  It is used later to tell apart entities with similar names.
- Predicates must be short verb phrases ("owns", "caused", "modified", "depends on").
- Every relation must connect two entities you extracted.
"""

def extract(text: str, src: str) -> ExtractedGraph:
    # output_format is the entire interface spec. No parsing. No silent errors.
    r = client.messages.parse(
        model=EXTRACT_MODEL, max_tokens=2048,
        messages=[{"role": "user",
                   "content": EXTRACT_PROMPT.format(text=text[:20000], src=src)}],
        output_format=ExtractedGraph,
    )
    return r.parsed_output

# ══ Stage 2 · entity resolution ══════════════════════════════════════
RESOLVE_PROMPT = """Below are {etype} entities extracted from several documents.
Some are different surface forms of the same real-world thing.

<entities>
{listing}
</entities>

Cluster them. Constraints:
- Every input name must appear in exactly one cluster's aliases (prevents silent loss)
- Genuinely distinct entities get their own singleton cluster (prevents over-merging)
- Do not merge on name similarity — judge from the descriptions
- canonical is the most complete, least ambiguous form
"""

def resolve(entities: list[Entity]) -> dict[str, str]:
    alias_map: dict[str, str] = {}
    for etype in set(e.type for e in entities):
        group = [e for e in entities if e.type == etype]
        # At scale, block here on cheap signals and process 50–100 at a time.
        listing = "\n".join(f'- "{e.name}": {e.description}' for e in group)
        r = client.messages.parse(
            model=REASONING_MODEL, max_tokens=4096,
            messages=[{"role": "user",
                       "content": RESOLVE_PROMPT.format(etype=etype, listing=listing)}],
            output_format=Resolved,
        )
        for c in r.parsed_output.clusters:
            for a in c.aliases:
                alias_map[a] = c.canonical

    # ★ Fallback: an unmatched name maps to itself. Without this, nodes vanish silently.
    for e in entities:
        alias_map.setdefault(e.name, e.name)
    return alias_map

# ══ Stage 3 · assembly ═══════════════════════════════════════════════
def build() -> nx.MultiDiGraph:
    docs = sorted(pathlib.Path("docs").rglob("*.md"))
    print(f"extracting from {len(docs)} documents…")
    raw = [(d.name, extract(d.read_text(encoding="utf-8"), d.name)) for d in docs]

    ents = [e for _, g in raw for e in g.entities]
    print(f"{len(ents)} raw entities → resolving…")
    amap = resolve(ents)

    G = nx.MultiDiGraph()   # Multi = several predicates allowed between two nodes
    for src, g in raw:
        for e in g.entities:
            n = amap[e.name]
            if n not in G:
                G.add_node(n, type=e.type, description=e.description, sources=[src])
            elif src not in G.nodes[n]["sources"]:
                G.nodes[n]["sources"].append(src)
        for r in g.relations:
            s, t = amap.get(r.source), amap.get(r.target)
            if s and t and s in G and t in G:
                # ★ Provenance: every edge carries its source. The premise of fact-checking.
                G.add_edge(s, t, predicate=r.predicate, source=src)

    # ══ Three diagnostics — always look before you use it ═══════════════
    comps = nx.number_weakly_connected_components(G)
    ratio = G.number_of_edges() / max(G.number_of_nodes(), 1)
    print(f"\nnodes {G.number_of_nodes()} · edges {G.number_of_edges()}")
    print(f"connected components {comps}  "
          + ("✓" if comps == 1 else "⚠ resolution may be incomplete (missing cross-document links)"))
    print(f"edges/nodes {ratio:.2f}   "
          + ("✓ healthy range" if 1.0 <= ratio <= 2.0 else "⚠ too sparse or too dense"))
    hubs = sorted(G.degree, key=lambda x: -x[1])[:5]
    print("hub nodes:", ", ".join(f"{n}({d})" for n, d in hubs))
    return G

# ══ Stage 4 · subgraph serialisation + a grounded answer ═════════════
def serialize(G, center: str, hops: int = 2) -> str:
    nodes, frontier = {center}, {center}
    for _ in range(hops):
        nxt = set()
        for n in frontier:
            nxt |= set(G.successors(n)) | set(G.predecessors(n))
        frontier = nxt - nodes
        nodes |= frontier
    lines = {f"({s}) --[{d['predicate']}]--> ({t})   # {d['source']}"
             for s, t, d in G.subgraph(nodes).edges(data=True)}
    return "\n".join(sorted(lines))

def ask(G, question: str, seed: str) -> str:
    ctx = serialize(G, seed, hops=2)
    prompt = f"""Answer using only the knowledge graph below.
Cite the specific edges that support your answer. If the graph does not
contain the answer, say so. Do not guess.

<graph>
{ctx}
</graph>

Question: {question}"""
    r = client.messages.create(
        model=REASONING_MODEL, max_tokens=800,
        messages=[{"role": "user", "content": prompt}],
    )
    return "".join(b.text for b in r.content if b.type == "text")

if __name__ == "__main__":
    if sys.argv[1] == "build":
        G = build()
        pathlib.Path("graph.json").write_text(
            json.dumps(nx.node_link_data(G), ensure_ascii=False, indent=2))
        print("\n→ saved graph.json")
    else:
        G = nx.node_link_graph(json.loads(pathlib.Path("graph.json").read_text()))
        seed = sorted(G.degree, key=lambda x: -x[1])[0][0]   # start at a hub
        print(ask(G, sys.argv[2], seed))

    "It runs on its own but I don't trust the output"L4A nodding loop. Put an independent evaluator in — the most common failure
    "It redoes today what it did yesterday"L4An amnesiac loop. A state file on disk
    "The context physically does not fit"L5Split the work into nodes, each with its own context
    "Several agents step on each other"L5Make writes single-threaded. Parallelise reading and proposing only
    "It can't answer questions spanning documents"L5A knowledge graph — but first check the decision table to see whether you really need one

    How far should you climb?

    The most common mistake is climbing too high People build loops where no loop is needed and graphs where no graph is needed. Every layer imposes a real maintenance cost. And an upper layer hides the problems of a lower one rather than fixing them — in fact it amplifies them.
    Stop hereWhenThe signal to move up
    Layers 1–2
    prompt + context    		Most individual work. Interactive is enough and you eyeball every result.The third time you repeat the same explanation
    Through layer 3
    + harness    		The same kind of work repeats. A team shares it. The result can be verified automatically.When pressing the run button is itself the bottleneck
    Through layer 4
    + loop    		Daily or weekly chores are clearly defined. You can build an independent evaluator.When the work is too big or too varied for one agent
    Layer 5
    + graph    		The context physically does not fit, several viewpoints are required, or you need large-scale parallelism.—
    The golden rule Do not climb to layer 4 if you cannot build an independent evaluator. Automation without verification is not automation; it is debt with speed attached. And going to layer 5 before layer 4 runs reliably multiplies the failure surface you have to debug.

    Intellectual balance — the case against

    This field is overheated. Here are the serious objections to each layer this guide has presented.

    "Prompt engineering is dead"

    Partly right. The 2024-vintage list of techniques really is dead. But both labs still maintain and expand their prompting guides in 2026, and OpenAI states explicitly that GPT-5.2 is "sensitive to prompting."

    "The harness is overrated"

    On benchmarks, there is something to it. METR and Scale AI data suggest that, holding the model constant, harness differences sit inside the margin of error. Noam Brown expects scaffolding to be superseded by model progress. But benchmarks contain no production database, no eight-minute test suite, and no payments code that requires review.

    "Loops are dangerous"

    Largely right. Wharton research: when the AI was wrong, participants accepted the wrong answer 73% of the time — and their confidence rose even when accepting a wrong answer. A Sonar survey: 96% of developers do not fully trust the correctness of AI code, yet only 48% always check it before committing.

    "Multi-agent is mostly a distraction"

    True of parallel writes. As of 2026 Cognition still regards parallel writer swarms as "mostly a distraction." They exempt parallel reading, review and voting.

    My synthesis: these five layers are not a ladder of capability but a ladder of automation scope. Climbing does not make anything smarter; it automates more, and further away. And whatever is automated becomes debt unless it is verified. Which is why one sentence keeps recurring in this guide — put something inside that can say "no." Only its form changes per layer: explicit constraints at layer 1, /clear at layer 2, tests at layer 3, an independent evaluator at layer 4, provenance and deterministic gates at layer 5.

    Glossary

    TermMeaning
    Attention budgetThe finite resource a model draws on when parsing large amounts of context. Every token you add consumes some of it.
    Context rotThe phenomenon whereby the ability to accurately recall information from context degrades as input length grows.
    CompactionSummarising a conversation that is nearing its limit and restarting in a fresh window. The first lever for long-horizon coherence.
    Just-in-time retrievalHolding only lightweight identifiers (paths, links) and loading what is needed at runtime, with tools.
    HarnessEverything in an AI agent except the model: tools, prompts, sandbox, hooks, permissions, observability.
    Skill · SKILL.mdA markdown file holding a procedure that loads only when needed. .claude/skills/<name>/SKILL.md. The directory name becomes the /command.
    SubagentA separate agent running in isolated context. Defined in .claude/agents/<name>.md, with permissions restricted via tools. It returns a summary, not the raw investigation.
    HookA check that runs as code on a lifecycle event, wired up in .claude/settings.json. Unlike skills and CLAUDE.md, which are advisory, hooks have force.
    MCP
    Model Context Protocol    		The standard for attaching external systems — issue trackers, databases, Slack — to an agent. "A USB-C port for AI applications."
    Fan-out / fan-inSplitting one input across several nodes to run at once / gathering those results back into one.
    LensThis guide's word for one independently executing agent. The "correctness lens" is not the name of a perspective but a separate agent instructed to look only through that perspective — with its own context, unable to see the other lenses' results. The count (N) is free; how to choose it is here.
    Stop conditionThe condition that decides whether a loop may finish. /goal checks it with a separate model after every turn. Used interchangeably with "completion condition" in this document.
    Guides / sensorsControls that give direction before action (feed-forward) / controls that observe after action and prompt correction (feedback).
    Progressive disclosureLoading a skill in three stages — metadata → instructions → resources — only as each is needed.
    WorktreeA git feature for having several independent working directories on one repository. File isolation for parallel agents.
    Generator / evaluatorSeparating the agent that writes from the agent that judges. The prescription for the structural failure of self-grading.
    Maker–checkerThe banking principle that whoever enters a large transfer must not be the one who reviews it.
    Intent debtThe recurring cost of re-explaining what this project is and what its rules are. Skills pay it down.
    Verification debtThe unverified output that piles up between "it runs" and "it is right".
    Comprehension rotThe widening gap between what exists in the codebase and what a human understands of it.
    Cognitive surrenderThe state in which the AI's output quietly becomes your output, and it no longer feels like there is anything left to check.
    Execution graphA graph of control flow. Nodes = work steps, edges = the route onward, state = data flowing along the edges.
    BarrierA synchronisation point that waits for all previous results before moving on. Only when genuinely required.
    Deterministic gateA checkpoint decided by code rather than a model: linters, typechecks, schema validation.
    Knowledge graphA structured, provenance-carrying representation made of entities (nodes) and typed relations (edges).
    Entity resolutionMerging different surface forms of the same real-world entity into a single canonical node.
    Multi-hop reasoningA question answerable only by connecting facts across several documents. In a graph, it becomes traversal.
    Subgraph serialisationConverting part of a graph into triple text that fits in a context window.
    ProvenanceThe record of which document and which extraction context each triple came from. The premise of fact-checking.
    Structured outputsThe API feature that forces a model response to validate against a schema (Pydantic / Zod).
